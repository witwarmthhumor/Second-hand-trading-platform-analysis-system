# 面试素材：项目中遇到的一个困难（RAG 问答「答非所问」的定位与修复）

> 用途：面试官问「讲一个你项目中遇到的困难 / 印象最深的一个 bug」时，直接照这份稿子口述。
> 主线口述约 2 分钟。第二节是可以直接背下来的原话；第三节讲「为什么这么讲」；第四节是追问预案。
> 所有数字都来自本仓库真实实测，可放心引用。

---

## 一、30 秒背景（开口前先交代，让面试官有画面）

这个项目是一个**二手交易平台的知识库问答系统**（RAG）：

- 语料：**920 篇**平台规则 / 指南 / 案例文档，切成 **7619 个**片段
- 检索：**向量（Chroma）+ BM25 关键词 + RRF 融合**的混合检索
- 问答链路有两条分支：检索到的最相关片段**相似度过门槛 → 直接把原文返回**；**过不了门槛 → 交给大模型生成回答**（这条叫「兜底」）
- 后端 FastAPI + PostgreSQL，前端 Vue 3，向量化用本地 bge-m3

一句话：**它是一个「能直答就直答、答不了才让大模型上」的系统。**

---

## 二、主线口述稿（可直接背诵）

### ① 抛出问题

「我想讲一个 RAG 问答系统里遇到的困难。

上线之后有用户反馈：他问『**你觉得转转这个平台怎么样**』，系统返回给他的，却是一段『**卖家要求私下转账怎么办**』的规则原文——完全是答非所问。更奇怪的是，答案下面的来源列表里，还挂着一条写着『**相关度 0.0%**』的引用。

我当时的第一反应是模型答错了。但我去看日志，发现一件很反直觉的事：**这条回答根本没有经过大模型。**

### ② 排查中的关键转折

我们这条链路有个设计：如果检索到的最相关片段相似度够高，就认为知识库里本来就有标准答案，直接把原文返回，这样更快、更省、也更忠实，不会被模型改写；只有相似度不够，才交给大模型去生成。

所以问题不在「生成」，而在「**判定**」——**系统误以为知识库里有一段现成的答案。**

### ③ 定位根因

我把这个问题的检索结果打出来看：

- 检索第一名是「**私下转账风险**」那篇 FAQ，**向量相似度 0.6235**（满分 1.0）
- 当时的命中门槛是 **0.55**，0.6235 过了线，于是被判成「命中」，原文被原样贴出去了

但 0.6235 这个分数，其实只代表『**有点沾边**』。用户问的是对**另一个平台**的评价，而我们的语料里根本没有『转转』的内容——全文只出现过两次，还都是顺带提及。检索引擎只能按笼统语义去找，结果找到了语义上最接近的『平台交易靠不靠谱』这一类文档，所以**正确答案应该是「未命中」→ 交给大模型据实说明**。

同时那条「0.0%」的来源我也查清了：那是 **BM25 靠关键词偶然命中、但语义完全不相干**的片段，它的向量相似度就是 0，之前的来源列表没做过滤，所以被展示了出来——属于无意义引用。

### ④ 关键决策：门槛定多少

找到根因之后，真正的问题是：**门槛应该定在多少？**

我没有拍脑袋，而是拿项目里 **285 条金标准问答**跑了一遍，统计每个问题检索第一名的相似度：

| 样本类型 | 最低相似度 |
|---|---|
| 领域内、检索正确的（261 条） | **0.6660** |
| 领域外、被误判的（24 条） | **0.6483** |

也就是说这两类之间天然存在一个 **0.6483 ~ 0.6660 的空隙**。我把门槛定在 **0.65**，正好落在这个空隙里——**正确的问题一个都没漏，同时把这类领域外的问题挡在了外面。**

我还测了继续往上调的代价，确认 0.65 是平衡点：调到 0.68 会漏判 6 条正确问题，0.70 漏判 23 条，0.75 漏判 104 条。

### ⑤ 落地与验证

修复分了四步：

1. **门槛从 0.55 提到 0.65**，并把取值依据写进代码注释，避免以后有人随手改
2. **来源列表按同一门槛过滤**，把那条 0.0% 的噪声引用去掉
3. **收敛重复实现**：非流式和流式两个入口原本各自复制了一份『命中判定 + 来源构造』的逻辑，我抽成了共用的 `build_hit_gate()`，防止以后两边规则漂移
4. **补 4 个回归测试**，全量 **162 个测试通过**

验证结果：这个『转转』的问题现在会正确走到大模型兜底、据实回答；领域内的问题命中不受影响；来源里的 0.0% 噪声消失。」

## 三、这个回答想体现什么（帮你理解为什么这么讲）

面试官问「困难」，实际在考察**你是怎么解决问题、怎么做决策的**。这段稿子刻意铺了五个层次：

| 层次 | 对应内容 | 想传递的信号 |
|---|---|---|
| 从现象出发 | 「答非所问」+「0.0% 来源」两个异常 | 能注意到细节，不被表象带偏 |
| 反直觉发现 | 这条回答**没经过大模型** | 不预设结论，用日志/数据验证假设 |
| 精确定位 | 相似度 0.6235 vs 门槛 0.55 | 能定位到具体的判定分支，而不是停在「模型不行」 |
| **数据驱动决策** | 285 条金标准测出 0.6483/0.6660 空隙 → 取 0.65 | 关键指标不靠感觉，靠分布说话（**这是最加分的部分**） |
| 工程收敛 | 抽公共函数 + 回归测试 | 不止修当下，还防未来复发 |

**最该强调的一句**：阈值不是拍的，是拿 285 条金标准跑出分布、找到空隙后定的，并且算清了继续上调的代价。

## 四、追问预案（面试官大概会问这些）

**Q1：为什么不用 RRF 得分做阈值？**
因为 RRF 是**排序融合分**，只表示相对排名，量级只有 0.016~0.033，没有绝对意义，定不了阈值。所以命中判定用的是**向量余弦相似度**（0~1，有绝对含义）。

**Q2：相似度 0.6235 是怎么算出来的？**
问题文本和文档片段分别过本地 **bge-m3** 模型得到向量，算**余弦相似度**。0.6235 表示语义上沾边但不相同。

**Q3：提高阈值，会不会有更多问题走大模型，导致成本和延迟上升？**
会，但影响可控：**只有落在 0.55~0.65 这个灰区的问题才会改变路径**。而实测领域内正确问题的最低分是 0.6660，所以领域内问题基本不受影响。另一面是，直出原文虽然零延迟零成本，但它只会照搬、答不了就是答不了；兜底虽然要调模型，但**能真正回答**。这是个明确的取舍。

**Q4：这个改动会不会影响检索质量指标（比如 RAGAS）？**
不会。这个阈值**只决定「直出原文 vs 大模型兜底」，不参与检索召回**，所以检索类指标（context recall / precision）不变。

**Q5：怎么保证以后不会退化？**
两层：一是 4 个针对性的回归用例（含灰区、边界值、0.0% 噪声过滤、空结果）；二是金标准扫描脚本可以随时重跑，重新看分布。

**Q6：如果语料更新了，0.65 还合适吗？**
不一定，**阈值应该和语料分布绑定**。我在代码注释里写明了取值依据，也留了「语料更新后重跑扫描脚本复核」这个动作。这也是我认可的一个遗留风险。

**Q7：为什么不干脆全部走大模型？**
一是成本和延迟（全量走模型每次都要调用、要等生成）；二是**忠实度**——直出原文是逐字引用，不会被模型改写或幻觉污染。知识库问答里「有标准答案就照抄」本身是更安全的选择。

**Q8：前端那个「0.0%」是怎么发现的？**
用户截图里带出来的。它和主问题是**两个独立根因**，只是恰好在同一个截图上，所以我分开修、分开验证。
