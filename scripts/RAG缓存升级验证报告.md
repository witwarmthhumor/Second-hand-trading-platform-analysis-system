## 一、A. 代码层验证

### 1.1 缓存设计合理性逐项判定

| 维度 | 现状 | 判定 |
| --- | --- | --- |
| 命中率关键路径 | key = `rag:search:{归一化问题}`，单 key `GET`，O(1)；命中后跳过 embedding + 向量检索 + BM25 + RRF 全链路 | ✅ 合理 |
| 缓存内容选择 | 缓存「检索结果 Top-K」而非 embedding 向量或最终答案 —— 正确的切面：一次命中同时省掉计算与检索，且不会缓存 LLM 幻觉 | ✅ 合理 |
| 归一化 | 全角→半角（整段减 0xFEE0）、去空白、小写；实测 4 种等价问法（含全角空格/前后空格/半角问号）**全部命中同一 key** | ✅ 有效 |
| TTL | 全局统一 `RAG_CACHE_TTL=3600s`，写时起算 | ⚠️ 可接受，但无随机抖动 |
| 序列化 | `json.dumps(..., ensure_ascii=False)` / `json.loads`，文本 JSON，无 pickle RCE 风险 | ✅ 合理 |
| 序列化开销 | 单条 value ≈ 2~5KB（top-5 × 900 字 chunk）；实测写入 0.38ms | ✅ 可接受 |
| 缓存失效 | 知识库重建后 `_run_rebuild` 按前缀 `SCAN` + `DEL` 清空 | ⚠️ 逻辑对，但实现有致命缺陷（见 1.2-②） |
| 连接池 | `from_url(decode_responses=True, socket_connect_timeout=2)` | ❌ 无 `max_connections`、无 `socket_timeout`、无健康检查 |
| 降级 | Redis 不可用时读写静默跳过，不影响问答主流程 | ❌ 无熔断，降级代价极大（见 1.2-③） |

### 1.2 实测确认的 4 个缺陷

#### ① 流式端点完全未接入缓存 —— 线上收益为 0（最严重）

```python
# backend/app/api/rag.py  ask_stream 的 event_stream()
results = retriever.search(payload.question, top_k=payload.top_k)   # ← 直接检索，绕过缓存
```

`rag_service.ask()` 走了缓存，但 `POST /api/rag/ask/stream` 没有；而前端 `App.vue:665` 调用的正是 `ragAskStream()`（`/api/rag/ask/stream`）。

> **结论：当前线上真实用户走的是流式端点，缓存收益 = 0。** 本报告测得的 3~12 倍提升，只在非流式端点（无前端调用方）或补上流式接入后才能兑现。

#### ② 跨事件循环复用 Redis 客户端 —— 重建后缓存永久失效

`kb._run_rebuild()` 在 BackgroundTasks 的同步函数里调用 `asyncio.run(get_search_cache().clear())`，这会新建并随后关闭一个事件循环；而单例 `_client` 的连接绑在那个已关闭的循环上。

实测（`improve/verify_loop.py`）：

```
循环 A（首次使用，建连）: 读到
读检索缓存失败：Event loop is closed
循环 B（新事件循环复用同一 client）: 未读到（缓存静默失效）
```

> **结论：执行一次「重建知识库」后，缓存会持续抛 `Event loop is closed` 并静默降级，直到进程重启才恢复。** 需在 `clear()` 后 `await client.aclose()` 并把单例 `_client` 置空。

#### ③ Redis 不可用时无熔断 —— 明确负优化

`_get_client()` 失败后 `_client` 仍为 `None`，**每次调用都会重新建连 + ping（socket_connect_timeout=2）**。实测（指向不可达端口）：

```
第1次 get: 2018 ms    第3次 get: 2005 ms
第2次 get: 2011 ms    第4次 get: 2009 ms
set: 2006 ms          clear: 2017 ms
```

> **结论：Redis 挂掉时，每个问答请求白白增加 2~4 秒（1 次 get，未命中再加 1 次 set），比不加缓存更慢。** 需要失败标记 + 熔断窗口（如失败后 30s 内不再尝试）。

#### ④ key 不含 `top_k` —— 结果串用

实测：

```
key = rag:search:担保交易是怎么运作的?
top_k=2 的请求实际拿到条数 = 5 （期望 2）
```

`ask()` 的 `top_k` 只影响「未命中时的检索条数」，却参与不了 key；同问题不同 `top_k` 的请求会互相覆盖缓存。

> 附带风险：key 也不含语料版本。若不走重建接口直接替换 `vector_store` 目录，TTL 内会读到旧语料结果（重建清空是唯一兜底）。

### 1.3 缓存穿透 / 击穿 / 雪崩防护评估

| 风险 | 现状 | 严重度 |
| --- | --- | --- |
| **穿透** | 无布隆过滤器、无空值标记。但向量检索恒返回 top-20，`results` 几乎不会为空，**空列表 `[]` 也会被正常缓存**（`if results is None` 判空逻辑对 `[]` 不成立），故实际穿透风险低 | 🟡 低 |
| **击穿** | **无 singleflight / 互斥锁**。热点 key 过期瞬间，N 个并发请求同时 miss 并同时打 Ollama | 🟠 中高 |
| **雪崩** | ① TTL 无随机抖动，同批写入的 key 会同时过期；② Redis 故障时全部流量回落 Ollama，且回落代价为 +2s/请求（见 ③） | 🔴 高 |

### 1.4 缓存生效 vs 无效 / 负优化场景

**✅ 真正生效**
- 高频重复 / 热点问法（FAQ、被反复问的同一问题）—— 命中率越高收益越大
- 知识库内可命中的问题（`vector_sim ≥ 0.55`，实测 0.78）→ 路径为「检索直出原文」，检索层就是端到端全部耗时，省 100% 检索耗时
- 语料静态、更新频率低 → TTL 内一致性风险低
- 多 worker / 多进程部署：Redis 外部化缓存天然共享（优于进程内 LRU）

**⚪ 无效**
- **前端默认走的 `/ask/stream` 未接缓存 → 收益 0**（见 1.2-①）
- 长尾、每次措辞都不同的问题 → 命中率 ≈ 0，只多付一次 `GET`（0.34ms）+ 一次 `SET`（0.38ms），实测提速 1.0x（172.3ms → 170.9ms，差异在噪声内）
- 检索未命中知识库、走 LLM 兜底的问题 → 端到端由 LLM（秒级）主导，缓存省下的 ~150ms 占比 < 5%（此项为推断，未调用付费 LLM 实测）

**🔴 负优化**
- Redis 不可用：每请求 +2~4s（见 1.2-③）
- 重建知识库后：缓存静默死亡（见 1.2-②）
- 重建时 `SCAN` 全量遍历 + 一次性 `DEL`，key 规模大时会阻塞 Redis（重建低频，可接受）

## 二、B. 数据层验证（实测）

### 2.1 组件微基准（各 20 次）

| 环节 | mean (ms) | p50 (ms) | p95 (ms) | 占完整检索比 |
| --- | ---: | ---: | ---: | ---: |
| **Ollama embedding（bge-m3）** | **92.47** | 90.51 | 113.01 | **61.8%** |
| BM25（jieba 分词 + 打分） | 26.24 | 28.25 | 30.25 | 17.5% |
| Chroma 向量 query | 2.33 | 2.20 | 2.82 | 1.6% |
| 其余（RRF + 17 次单点 `collection.get` + Python 开销） | ≈28.5 | — | — | 19.1% |
| **完整检索（miss 路径）** | **149.57** | 151.77 | 160.48 | 100% |
| Redis 命中读 | 0.34 | 0.34 | 0.38 | — |
| Redis 写入 | 0.38 | 0.38 | 0.43 | — |

> 额外发现（非缓存问题，但值得记录）：BM25 分支对每个不在向量结果里的命中会单独 `collection.get(ids=[f"c{i}"])`，实测 **每次检索约 17 次单点查**（`chroma` 调用数 1027/60 ≈ 17.1），呈 N+1 模式。这批开销也一并被缓存省掉（约 28ms/次）。

### 2.2 三种工作负载：加缓存前 vs 加缓存后

请求数各 60，顺序执行，单位 ms。

| 工作负载 | 命中率 | 缓存前 mean / p95 | 缓存后 mean / p95 | 提速 | QPS 前 → 后 | embed 调用 | Chroma 调用 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| W1 全量穿透（问法全不同） | 0.0% | 172.34 / 195.60 | 170.94 / 186.05 | **1.0x** | 5.80 → 5.85 | 60 → 60 | 1027 → 1027 |
| W2 热点 80/20 | 71.7% | 140.18 / 179.09 | 45.61 / 182.99 | **3.1x** | 7.13 → **21.92** | 60 → **17** | 1017 → **285** |
| W3 完全重复（FAQ） | 91.7% | 129.66 / 163.60 | 10.67 / 117.77 | **12.2x** | 7.71 → **93.68** | 60 → **5** | 1008 → **84** |
| 并发 8-W2（wall time） | 71.7% | p95 689.17 / 3.541s | p95 622.33 / 1.529s | QPS **2.3x** | 16.94 → **39.24** | 60 → 22 | 1017 → 379 |

关键观察：
- **下游调用量按命中率线性下降**：W3 中 embedding 从 60 次降到 5 次（-91.7%），Chroma 从 1008 次降到 84 次（-91.7%），与命中率完全吻合 → 缓存确实在源头拦截，而非仅"返回更快"。
- 缓存后 p95 仍偏高（117.77ms / 622.33ms），因为 p95 落在了 8.3% 的未命中请求上——未命中请求依旧是完整检索耗时。**这说明提均值靠命中率，提 p95 要靠预热或 singleflight。**

### 2.3 DB 负载归因（重点：缓存并不省 Postgres）

| 资源 | 缓存前 | 缓存后 | 变化 |
| --- | ---: | ---: | --- |
| Ollama embedding 调用 | 60 | 5（W3） | **-91.7%** |
| Chroma 查询次数 | 1008 | 84（W3） | **-91.7%** |
| BM25 检索次数 | 60 | 5（W3） | **-91.7%** |
| **Postgres 查询/写入** | 每次 1 次竞品上下文查询 + 会话读写 | **完全不变** | **0%** |

> `api/rag.py` 的 `_load_competitors_context()` 与 `_save_session()` 在每次问答都会落库，**缓存层完全没有覆盖 Postgres**。所以「DB 负载下降」这个说法在本项目里不成立——降的是 embedding 计算与向量库/BM25 检索负载，不是关系库负载。

### 2.4 提升幅度与归因

单次命中省下：`149.57ms（完整检索） - 0.34ms（Redis 读） = 149.23ms`

| 归属 | 省下耗时 | 占比 | 性质 |
| --- | ---: | ---: | --- |
| Ollama bge-m3 embedding | 92.47ms | **62.0%** | 省**计算**（模型推理 + HTTP 往返） |
| BM25（jieba 分词 + 打分） | 26.24ms | 17.6% | 省**检索** |
| Chroma 向量 query + 17 次单点点查 + RRF | ≈30.5ms | 20.4% | 省**检索/DB 查询** |
| 合计 | 149.23ms | 100% | 计算 62% / 检索 38% |

**归因结论：省下的时间里 62% 是"省计算"（embedding 推理），38% 是"省检索/向量库查询"。与 Postgres 无关。**

| 工作负载 | 延迟降幅 | QPS 提升 |
| --- | ---: | ---: |
| W1 全量穿透 | +0.8%（噪声） | +0.9%（噪声） |
| W2 热点 80/20 | **-67.5%** | **+207%** |
| W3 完全重复 FAQ | **-91.8%** | **+1115%** |

## 四、一句话结论

**热点/FAQ 问法下整体提升 207%（QPS 7.13→21.92，延迟 140ms→46ms），主要来自省掉 Ollama bge-m3 embedding 推理——它占省下耗时的 62%，其余 38% 来自省掉 BM25 与 Chroma 检索；但前端默认走的流式端点尚未接入缓存，线上真实收益目前为 0。**

## 五、还能继续优化的 3 个点

| # | 优化点 | 为什么优先 | 预期收益 |
| --- | --- | --- | --- |
| **1** | **把缓存接入 `/api/rag/ask/stream`，并把 `top_k` 与语料版本纳入 key** | 前端默认走流式，不接入则前面所有收益归零；key 缺 `top_k` 已被实测证明会结果串用 | 让 3~12 倍提升真正落到线上；消除结果串用（正确性修复） |
| **2** | **补 Redis 熔断 + 修复跨事件循环**：失败后 30s 内不再重试；`clear()` 后 `aclose()` 并置空单例；配置 `socket_timeout` / `max_connections` | 已实测两处硬伤：Redis 挂掉每请求 +2~4s（比不加缓存更差）；重建知识库一次即导致缓存永久静默失效 | 消除负优化；把"重建后缓存必死"变成"重建后自动恢复" |
| **3** | **防击穿/雪崩 + 顺手修检索 N+1**：热点 key 加 singleflight（并发 miss 只放 1 个请求回源）、TTL 加 ±10% 随机抖动、加进程内 LRU 作二级缓存；把 BM25 分支的逐条 `collection.get` 改为一次批量 `get` | 缓存后 p95 仍高（117~689ms）全部落在 miss 请求；N+1 已实测每次检索约 17 次单点查 | 未命中请求也不被击穿；单次检索再省约 28ms（19%），对长尾（缓存无效场景）同样有效 |
