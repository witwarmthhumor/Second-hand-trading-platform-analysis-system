# 后续开发计划（v1.4 候选方向）

> 当前版本：v1.4.0（本文档方向一~三已落地：RAG 检索缓存 / LLM 流式输出 / Alembic 迁移，149 用例通过）

## 背景与取舍

梳理出的后续方向很多，本文档聚焦 **投入产出比最高、风险可控** 的三项，其余列在文末「候选池」供后续挑选。

核心判断：问答是用户最高频的功能，围绕它做「省成本 + 提体验」收益最直接。

## 方向一：RAG 检索缓存（省成本、降延迟）

### 价值
相同/相似问题重复做 embedding + 向量检索，热点问题命中缓存可显著降低延迟与计算开销。

### 方案
- 引入进程内 LRU 缓存（`functools.lru_cache` / 自研带 TTL 的 LRU），按「问题文本归一化后」作为 key，缓存检索结果（Top-K + 来源）。
- 归一化：去首尾空白、全角转半角、统一标点，避免「忘记密码」与「忘记密码！」算两个 key。
- 缓存命中直接返回上次检索结果；未命中走原检索流程并写缓存。
- 容量与失效：固定容量（如 512 条）+ TTL（如 1 小时），知识库重建时主动清空缓存。

### 分阶段
1. 实现缓存层（TTL LRU），接入 `retriever.search` 前
2. 知识库重建接口触发时清空缓存
3. 补单测：命中返回一致、过期失效、重建清空

### 验收标准
- 相同问题第二次查询命中缓存，不再触发 embedding
- 知识库重建后缓存被清空，新结果生效
- 相关单测通过，ruff 通过

## 方向二：LLM 流式输出（SSE，提体验）

### 价值
现在兜底回答整段返回，长回答要等。改流式可做到「首字秒出」，体验接近 ChatGPT。

### 方案
- 后端 `POST /api/rag/ask` 增加流式模式：命中知识库仍直出（无需流式）；未命中走 LLM 兜底时，用 `StreamingResponse` + SSE 逐 token 推送。
- LLM 请求加 `stream: true`，逐 chunk 解析 `delta.content` 并 yield。
- 新增 `POST /api/rag/ask/stream` 端点（或 ask 加 `stream` 参数），保留原非流式端点兼容。
- 成本记账：流式结束后按 usage 一次性 `tracker.record`（与现在一致）。

### 分阶段
1. 后端：`_llm_fallback` 增加流式生成器，新增流式端点
2. 前端：`fetch` + `ReadableStream` 解析 SSE，气泡逐字渲染
3. 打字动效与「停止生成」按钮

### 验收标准
- 流式接口逐 token 返回，前端气泡逐字渲染
- 非流式接口行为不变（回归通过）
- 成本记账与流式前一致，无重复/遗漏
- 相关单测通过，ruff 通过，前端 build 通过

## 方向三：数据库迁移 Alembic（补技术债）

### 价值
现在靠 `Base.metadata.create_all` 建表，改模型不会自动迁移表结构（此前加 user_id 是手动清空重建）。数据多了再改表会踩坑，越早补越省事。

### 方案
- 引入 Alembic，初始化迁移环境，配置为 async engine。
- 生成首个 baseline 迁移（对应当前所有模型），后续模型变更走 `alembic revision` + `upgrade`。
- `init_db` / lifespan 改为「迁移 + seed」，不再 `create_all`（保留测试环境 `create_all` 快速建表）。

### 分阶段
1. 引入 Alembic + async 配置 + baseline 迁移
2. lifespan 改为迁移驱动，测试环境保留 create_all
3. 验证：空库能迁移到当前结构、现有库 upgrade 幂等

### 验收标准
- 空库 `alembic upgrade head` 得到完整表结构
- 现有开发库 upgrade 不报错、数据不丢
- 全量测试通过（测试仍走 create_all，互不影响）

## 建议实施顺序

1. **方向一（RAG 缓存）** — 收益直接、风险最低，可独立先行
2. **方向二（LLM 流式）** — 体验提升明显，前端工作量稍大
3. **方向三（Alembic）** — 技术债，穿插在功能迭代间隙补

> 三项相互独立，可按需裁剪或调序。确认后我按「先出最小可用 → 分阶段落地 → 每阶段验证」执行。
