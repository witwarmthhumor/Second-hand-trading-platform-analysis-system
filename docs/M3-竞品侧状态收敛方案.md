# M3 竞品侧共享状态收敛方案

> 状态：待评审。零 RAG 耦合，可与并行会话并行推进。
> 前置：M1 已完成（App.vue 从 1765 行拆薄为 748 行，7 个 tab 独立组件）。

## 1. 结论

用 **Vue3 组合式函数 + 模块级单例**（**不引入 Pinia**），把 App.vue 里 6 个跨组件状态收敛到 `src/stores/competitor.js`。组件改为直接从 store 读写，砍掉 App ↔ 子组件之间的 props / events 传递链。

## 2. 现状问题（为什么做）

App.vue 第 164–242 行集中了 6 个共享状态，靠「props 下发 + 事件上抛」在 7 个组件间流动：

| 状态 | 载体 | 消费者 | 痛点 |
|---|---|---|---|
| `pendingCount` | prop 下发 + `@count`/`@changed` 上抛 | 侧栏徽标、列表统计卡 | **双通道刷新**：`@count` 直接赋值，`@changed` 又触发重查；一次 approve 会触发 2~3 次更新、可能竞态 |
| `ratingDims` | prop 下发 + `@saved` 上抛 | 表单、设置页 | App 负责加载，设置页改完靠 `onDimsSaved` 回写，链路绕 |
| `formTarget`/`formKey` | prop 下发 + `@edit` 上抛 | 录入表单 | 编辑对象 + 强制重建 key 绑定在一起，职责不清 |
| `compareIds` | prop 下发 + `@compare` 上抛 | 对比面板 | 列表勾选 → App → 对比面板，三级传递 |
| `ragReady`/`ragChatKey` | prop / 直接状态 | 顶栏、RagChat | 与竞品无关但混在壳层 |

**两个具体的「改 A 坏 B」隐患：**

1. `CompetitorList` 用 `v-if="activeTab==='list'"`，**靠切 tab 重新挂载来刷新列表**。`onFormSaved` 的注释明确写了这点——一旦未来把 `v-if` 改成 `v-show` 或加 keep-alive，列表就会「保存后不刷新」。
2. 数据变更的传播靠 `emit('changed')` 链式上抛，新增一个会改数据的组件（如批量操作）时，很容易漏发事件导致徽标/列表不同步。

## 3. 选型对比

| 方案 | 依赖 | 迁移成本 | 收益 | 结论 |
|---|---|---|---|---|
| **A. 组合式函数单例** | 零 | 低（纯挪状态） | 消除 props/events 链、统一数据流 | ✅ **推荐** |
| B. Pinia | +1 依赖（`pinia`） | 中（要装依赖、改 `main.js`、全部组件改 import） | devtools/插件/更好的 TS 支持 | 暂不需要：前端无测试基建、无 TS，这些优势用不上 |
| C. 维持现状 | 零 | 零 | — | 继续累积耦合 |

**何时再上 Pinia**：出现「需要 devtools 时序调试」「跨页面持久化缓存」「SSR」中的任一需求时再迁；届时 store 的 state/action 形状可直接映射过去，迁移成本可控。

## 4. 详细设计

### 4.1 store 结构（`src/stores/competitor.js`）

```js
import { ref } from 'vue'
import { competitorApi } from '../api'

// —— 状态（模块级单例：所有 import 处共享同一份）——
const pendingCount = ref(0)
const ratingDims = ref([])
const formTarget = ref(null)   // null=新建；否则为待编辑行
const formKey = ref(0)         // 变化即强制重建表单
const compareIds = ref([])

// —— 数据变更通知：用版本号，不用回调（组件卸载后不留悬挂引用）——
const listVersion = ref(0)     // 竞品列表监听，自增后重拉
const pendingVersion = ref(0)  // 待校对页监听，自增后重拉

// —— actions ——
async function refreshPendingCount() {
  try {
    const rows = await competitorApi.list({ data_status: '待校对' })
    pendingCount.value = rows.length
  } catch { /* 非关键，静默 */ }
}

async function loadRatingDims() {
  const r = await competitorApi.getRatingDimensions()
  ratingDims.value = r.dimensions
}
function setRatingDims(dims) { ratingDims.value = dims }

function openCreate() { formTarget.value = null; formKey.value++ }
function openEdit(row)  { formTarget.value = row;  formKey.value++ }
function startCompare(ids) { compareIds.value = ids }

// 任何「改了竞品数据」的动作只调这一个：统一触发列表 + 待校对 + 徽标三处同步
function notifyChanged() {
  listVersion.value++
  pendingVersion.value++
  refreshPendingCount()
}

export function useCompetitorStore() {
  return { pendingCount, ratingDims, formTarget, formKey, compareIds,
           listVersion, pendingVersion, refreshPendingCount, loadRatingDims,
           setRatingDims, openCreate, openEdit, startCompare, notifyChanged }
}
```

### 4.2 组件改动点

| 文件 | 改动 |
|---|---|
| **App.vue** | 删除第 164–242 行的 6 个状态与 `refreshPendingCount`/`loadDims`/`on*` 事件处理器；**保留** `activeTab`/导航/登录态（导航是壳层职责）。跳转动作改为「调 store 的 action + 设 activeTab」 |
| `CompetitorList.vue` | 删 `props.pendingCount`、`emit('create/edit/compare/changed')`；改为 `store.pendingCount` 只读、`store.openCreate()/openEdit()/startCompare()`、`store.notifyChanged()`；`watch(listVersion)` 重拉列表 |
| `PendingReview.vue` | 删 `props.refreshKey`、`emit('count/edit/changed')`；`watch(pendingVersion)` 重拉；增删改后 `store.notifyChanged()` |
| `CompetitorForm.vue` | 删 `props.model/dims`；从 `store.formTarget`/`store.ratingDims` 读；保存/取消 emit 保留（App 用它切回 list） |
| `ComparePanel.vue` | 删 `props.ids`；从 `store.compareIds` 读 |
| `SettingsPanel.vue` | 删 `props.dims`；读 `store.ratingDims`，保存后 `store.setRatingDims()` |
| `RagChat.vue` | 不动（`ragReady`/`ragChatKey` 属于 RAG，且本方案不碰 RAG 区；如要收，另开 M3-RAG，避免踩并行会话地盘） |

### 4.3 数据流约定（防「改 A 坏 B」的规范）

1. **`pendingCount` 只有一个写入方**：`store.refreshPendingCount()`。组件绝不直接赋值。
2. **改数据的组件只调 `store.notifyChanged()`**，不关心谁要刷新。
3. **列表/待校对的刷新由 `listVersion`/`pendingVersion` 驱动**，不再依赖 `v-if` 重挂载。
4. **导航（activeTab）留在 App.vue**，数据状态全部进 store——职责边界：壳层管「在哪页」，store 管「什么数据」。

## 5. 实施步骤（每步独立 commit + 验收）

| 步 | 内容 | commit | 验收 |
|---|---|---|---|
| 1 | 新建 `src/stores/competitor.js`，抽 `pendingCount` + `ratingDims` + 相关 action；App.vue 与 List/Pending/Form/Settings 改为读 store | `refactor(frontend): 引入 competitor store，收敛 pendingCount/ratingDims` | build 通过 + 徽标/统计卡/设置页正常 |
| 2 | 收敛 `formTarget/formKey/compareIds`，List 跳转、Compare 读 ids 改走 store | `refactor(frontend): 表单编辑态与对比选中收敛入 store` | build 通过 + 录入/编辑/对比跳转正常 |
| 3 | 引入 `listVersion/pendingVersion`，列表与待校对改为版本号驱动刷新，删除 `v-if` 重挂载依赖与 `@changed` 链 | `refactor(frontend): 数据变更通知改版本号驱动，消除重挂载依赖` | build 通过 + 增删改后列表/徽标/待校对三处一致 |
| 4 | 清理 App.vue 残留事件处理器，复核无死代码；全文 grep 确认无遗留 props/emit 链 | `chore(frontend): 清理 M3 残留 props/emit` | build 通过 + CDP 7 tab 回归 |

每步完成后 `npm run build` 必须通过；`ragReady`/`ragChatKey` 与 RagChat 全程不动。

## 6. 验收标准

1. `npm run build` 零报错。
2. CDP 回归 7 个 tab（沿用 `cdp-ui-verify` 技能）：登录 → 列表 → 待校对 → 录入/编辑 → 对比 → 知识库问答 → 设置，各页无未捕获异常。
3. 行为断言：
   - 列表页「抓取竞品」成功后，侧栏徽标 +1，切到待校对页能看到新草稿；
   - 待校对页「确认入库」后，徽标 -1，切回列表能看到该竞品；
   - 设置页改评分维度后，录入表单的维度立即同步。
4. `grep -rn "emit('changed')\|:pending-count\|:dims=\|:model=\|:ids=" frontend/src/components/` 返回空（旧链已清零）。

## 7. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 模块级单例在 HMR 下状态丢失/重复 | Vite 对 `.js` 模块默认热替换，改 store 后刷新页面即可；开发期影响可接受 |
| 单例在组件卸载后仍存活（内存） | 状态量小（几 KB），无累积；`listVersion` 用版本号避免悬挂回调 |
| 与并行会话前端改动冲突 | 前端目前无并行活动（对方在 RAG 区）；提交前 `git status` 圈定 `frontend/src` 范围，避开他人在途文件 |
| 回滚 | 每步一个 commit，任一步出错 `git revert <commit>` 即可退回上一稳定态 |

## 8. 范围外（明确不做）

- 不引入 Pinia、不装任何新依赖。
- 不动 `ragReady`/`ragChatKey`/RagChat（避免踩 RAG 地盘）。
- 不重构 api.js 错误处理（那是 M4，独立的一档）。
