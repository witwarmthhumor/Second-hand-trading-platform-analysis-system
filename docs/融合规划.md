> 本文档是把「竞品分析系统」（Agent）与「RAGreflow 二手交易知识库」（RAGreflow-second-hand）两个项目

## 一、目标

把现有「古玩·钱币竞品分析系统」改造为「**二手交易平台分析系统**」，并在其中**融入 RAG 知识库问答能力**，
最终形成一个同时具备两种能力的单系统：

1. **竞品分析**：对二手交易平台（闲鱼、转转、爱回收）做 CRUD、对比雷达图、报告导出（复用现有能力，改领域）。
2. **知识库问答**：基于 RAGreflow 的 1000 份二手交易语料，提供规则类问答（检索 + 来源 + LLM 兜底）。

## 三、关键技术事实（读代码后的客观结论）

> 必须如实记录，避免后续误判：

1. **B 项目的检索链路实际上没有用 LangChain**：尽管 `requirements.txt` 声明了 langchain，但
   `retrieval_eval/__main__.py` 的实际实现是 `chromadb` 原生客户端 + `rank-bm25`（BM25Okapi）
   + **手写 RRF 融合** + 直接调 Ollama `/api/embed`。LangChain 是「装而未用」。
2. **检索参数（经 B 项目 S6 评测验证）**：chunk_size 最优 900、RRF k=60、Chroma cosine 距离、
   每块注入《文档标题》（解决标题信息丢失）、FAQ 以「条」为块。
3. **混合检索指标**：Hit@5 0.9965 / MRR@10 0.9544（同源数据，偏乐观，已声明）。

**因此「用 LangChain」的落地方式有两种**，实施时需再次确认：
- **路径 A**：沿用 B 已验证的手写检索链路（chromadb + rank-bm25 + RRF），
  只新增一个轻量 `rag` 服务封装，挂到 FastAPI。LangChain 作为可选依赖不强制。
- **路径 B（已选定 ✅）**：真正引入 LangChain 的 Retriever/Chain 抽象重构检索，
  用 LangChain 的 Embeddings + Chroma VectorStore + 检索器组合实现混合检索。
  注意：这与 B 的已验证参数不完全一致，需要重新评测或做等价性对齐。

### 沿用（现有成熟）

| 层 | 选型 | 说明 |
|----|------|------|
| Embedding | bge-m3（Ollama `/api/embed`） | 1024 维，与 B 一致 |
| 向量库 | ChromaDB（PersistentClient） | 复用 B 评测成果 |
| 关键词检索 | rank-bm25 + jieba + glossary 词典 | 复用 B |
| 混合融合 | RRF（k=60） | 复用 B |
| 答案生成 | 检索直出 + LLM 兜底（复用现有 Provider） | 见决策 |

## 七、风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| bge-m3 拉取中断/慢 | 阶段 F2 阻塞 | 后台拉取 + 断点续拉；已有 nomic-embed-text 可临时降级 |
| Chroma/依赖版本冲突 | 后端环境冲突 | 单独 venv 或用 uv 锁版本；RAG 依赖与现有隔离评估 |
| 领域切换遗漏文案 | 前端残留「古玩/钱币」 | 全局搜索替换 + 前端人工核对 |
| 检索未命中时 LLM 兜底成本 | 额外 API 费用 | 复用成本熔断；兜底可关闭 |
| 1000 份语料建库耗时 | 首次建库慢 | embedding 落盘缓存，二次建库秒级 |
