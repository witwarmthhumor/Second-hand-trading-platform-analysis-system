# 实施计划

> 二手交易平台分析系统 — 分阶段实施与验收
> 本文是「做什么」（产品设计文档）与「怎么做」（技术方案）的实施落地，聚焦分阶段推进与验收标准。
> 技术选型以 `docs/技术方案.md` 为准（如 PostgreSQL 而非 SQLite、Vue 3 而非待定）。

## 一、实施原则

- **分阶段推进**：每阶段先出该阶段的详细改动清单，确认后再写代码。
- **每步实测**：每次改动后实际运行/测试，报告真实结果，不写「应该能用」。
- **不擅自扩展**：新想法记入待办，不顺手实现；严格按 MVP 收敛。

## 二、最小可用版本（MVP）范围

**一句话**：一个本地 Web 系统，能手动录入 + 半自动抓取二手交易平台竞品信息，AI 提炼结构化数据，并在一个页面上完成多竞品横向对比。

**只做**：
1. 竞品数据增删改查（手动录入为主）。
2. 通用分析维度字段。
3. 单页对比视图（对比表 + ECharts 雷达图）。
4. 一个抓取试点：1~2 个站点，抓取 → LLM 提炼 → 人工校对入库。
5. 简单前端页面（列表页 + 对比页 + 录入表单）。

**明确不做**：用户登录/权限、自动定时监控、复杂报表导出、多租户、云端部署、移动端。

## 三、分阶段计划与验收标准

### 阶段 0：工程骨架搭建

**内容**：项目目录、虚拟环境、FastAPI 空服务、数据库连接、前端 Vite 脚手架、README 与架构图。

**验收标准**：
- [ ] `uvicorn` 启动后端，`/docs` 可访问，`/health` 返回 200。
- [ ] 前端 `npm run dev` 启动，能请求到后端接口。
- [ ] 数据库可正常建表（空表）。

### 阶段 1：竞品数据模型 + CRUD API + 录入页

**内容**：通用字段模型（含扩展 JSON 字段）、Pydantic schema、CRUD 接口、前端列表页 + 录入表单。

**验收标准**：
- [ ] 通过 API 能完整增删改查竞品。
- [ ] 前端能录入一条竞品并回显列表。
- [ ] 字段校验生效（类型错误被拦截）。
- [ ] pytest 覆盖 CRUD 核心用例通过。

### 阶段 2：半自动抓取 + LLM 提炼 + 人工校对

**内容**：爬虫模块（httpx + BeautifulSoup4）、LLM Provider 抽象层、抓取→提炼→「待校对」→人工确认入库。

**验收标准**：
- [ ] 输入 1 个试点 URL，能抓到页面正文。
- [ ] LLM 能抽出结构化字段 + 摘要（输出经 Pydantic 校验）。
- [ ] 提炼结果进入待校对状态，人工确认后才正式入库。
- [ ] 抓取/LLM 失败时降级为手动录入，不报错中断。

### 阶段 3：多竞品对比 + 雷达图

**内容**：对比查询接口、前端对比页（表格 + ECharts 雷达图）。

**验收标准**：
- [ ] 选择 ≥2 个竞品，能生成对比表。
- [ ] 雷达图正确渲染多维度对比。
- [ ] 对比维度可配置（默认通用维度）。

### 阶段 4（可选，MVP 之后）：定时监控 + 报告导出

**内容**：APScheduler 定期抓取更新、变化记录、导出 Markdown/HTML 报告。

**验收标准**：另行确认后启动（不进 MVP）。

## 四、风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 反爬/登录墙 | 抓取失败 | 降级为人工录入，不阻塞主流程 |
| LLM 接口不确定 | 提炼环节受阻 | Provider 抽象层 + 规则提取兜底 |
| 竞品维度发散 | 字段设计返工 | 先定最小通用字段集，扩展字段用 JSON 存 |
| 范围蔓延 | 项目做不完 | 严格按 MVP 收敛，扩展功能后置 |
| 单阶段工作量过重 | 前后端耦合 | 前端先做「够用」的后台，美化后置 |

## 五、每阶段结束的输出约定

每阶段结束明确列出：
1. **已验证** / **未验证** / **剩余风险**。
2. 真实运行/测试结果。
