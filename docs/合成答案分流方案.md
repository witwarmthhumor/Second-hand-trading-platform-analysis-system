## 一、一句话结论

**生产 `ask()` 命中即「直出 top1 原文」，top-5 的唯一消费者是来源列表；本方案把消费者扩展为两个——来源列表继续用广度视图（配额 1，现网不变），新增「合成答案」路径用深度视图（配额 4）作上下文，并按可配置的分流规则决定哪些命中走合成。全程有开关（默认 `off`）、有降级（合成失败回直出）、有验收（生成侧 A/B 分桶判定后才定默认档位）。**

## 二、现状与证据链

### 2.1 生产路径（`rag_service.ask()` / `api/rag.py::ask_stream`）

```
retrieve(question, top_k=5)          # 带缓存 + singleflight
  └─ HybridRetriever.search()        # 一次 embedding → 向量+BM25 → RRF
       └─ diversify_with_refill(ranked_all, ..., anchor_quota=ANCHOR_QUOTA)   # 全局唯一配额
build_hit_gate(results)
  ├─ 命中（results[0].vsim ≥ 0.65）→ 直出 results[0]["text"] + sources（doc 去重 + 阈值过滤）
  └─ 未命中 → 三档：灰区注入调 LLM / 拒答不调 LLM（4baaba1，本轮不动）
```

### 2.2 已裁定的证据（本方案的地基）

| 结论 | 来源 | 对方案的含义 |
|---|---|---|
| 配额 1→4 使合成 faith 0.7907→0.9662、relev 0.7398→0.9078；**差距几乎全来自拒答率 20%→0** | `116b933`（40 问，¥1.28） | 深度上下文是合成上线的硬前置 |
| 配额 4 会牺牲来源列表广度（用户可见来源覆盖 0.7873→0.7416） | `116b933` | 不能全局切 4 → 必须双视图 |
| 合成 v1 提示词（正文内联【来源:x】）faith 0.9682 优于 v2 0.9439 | `746ebbc` | 合成 prompt 直接复用 v1，不重新发明 |
| bge-m3 相似度无法区分问题类型（分布严重重叠） | `a063126`（gate_band_probe） | 分流判据**不能用相似度阈值**，要用检索结果的被动信号 |
| 直出基线（现网）：faith 0.9944 / relev 0.8455 / coverage 0.6025 | `746ebbc` | 合成的预期收益 = relev/coverage；直出的护城河 = faith=1、零延迟、零成本 |
| 未命中的三档分流已闭环（领域内零误伤/领域外零漏挡） | `d372aad` | 本方案只动「命中」分支，未命中路径零改动 |

### 2.3 核心可行性：双视图零额外检索成本

`diversify_with_refill` 是**纯函数**（输入全量 RRF 候选 `ranked_all` + 配额，输出 top_k 名单）。同一份候选池（一次 embedding + 一次 RRF 的产物）可以分别以配额 1 和配额 4 各调一次：

- **广度视图**（配额 1）：= 现网行为，`results[0]` 不变、来源列表不变；
- **深度视图**（配额 4）：top1 文档占 4 块 + 其余各 1，供合成上下文。

不需要第二次向量检索，纯内存名单重排，CPU 开销可忽略。

## 三、核心设计

### 3.1 检索层：`search_dual()`

```python
# retriever.py（新增，不改 search() 既有契约）
def search_dual(self, query: str, top_k: int) -> tuple[list[dict], list[dict]]:
    """一次检索，返回 (广度视图, 深度视图)。
    广度 = diversify_with_refill(..., anchor_quota=BREADTH_QUOTA)；深度 = anchor_quota=DEPTH_QUOTA。
    search() 保持现网契约，等价于 search_dual()[0]。"""
```

新常量（`rag/config.py`，**不复用** `ANCHOR_QUOTA` 以免语义混淆）：

```python
BREADTH_QUOTA = int(os.getenv("BREADTH_QUOTA", str(ANCHOR_QUOTA)))  # 默认 1，= 现网
DEPTH_QUOTA   = int(os.getenv("DEPTH_QUOTA", "4"))                  # 合成上下文用
```

验收红线：**广度视图与现网 `search()` 输出逐位一致**（单测对拍守卫，参照 `test_doc_chunk_ids_与bm25索引逐位对拍` 的做法）。

### 3.2 服务层：分流规则（`SYNTH_MODE`，默认 off）

```python
SYNTH_MODE = os.getenv("SYNTH_MODE", "off")   # off | multi_doc | all
```

| 档位 | 命中后的行为 | 依据 |
|---|---|---|
| `off`（默认） | 全部直出，**现网逐字节不变** | 116b933 裁定：无合成消费者时不牺牲现网 |
| `multi_doc` | 广度视图 sources **≥ 2 篇** → 合成；否则直出 | 多文档信号来自检索结果本身（零成本、不依赖相似度阈值）；单文档问题留给直出（faith=1、零延迟） |
| `all` | 命中即合成 | 体验统一；faith 从 1.0 降到 ~0.97 + 每问 LLM 成本 + 1~3s 延迟，须 A/B 证明值得 |

设计取舍说明：

- **为什么判据是「sources 篇数」而不是问题分类器/相似度**：P0-2 已证伪「bge-m3 相似度可做细粒度分级」；引入 LLM 分类器 = 每问多一次调用（成本/延迟翻倍）；关键词规则脆弱。`sources` 篇数是检索结果自带的被动信号——多文档问题（如「闲鱼和转转哪个验机更严」）去重后天然落在多篇文档上。
- **单文档问题为何留给直出**：直出 faith=1.0、零延迟零成本；其 coverage 短板（0.6025）主要伤「答案完整性」，是否可接受由 A/B 分桶数据裁定，不预设结论。

### 3.3 合成与降级

- **上下文**：深度视图（配额 4）的 5 条 chunk，带【doc_id】标签拼装（复用 `gen_answers.build_synth_messages` 的拼装格式）。
- **提示词**：照搬评测已验证的 `SYNTH_SYSTEM_PROMPT`（v1，`746ebbc` 上线选 v1）。
- **LLM 调用**：新增 `_llm_synthesize()` / `_llm_synthesize_stream()`，骨架复用 `_llm_fallback(_stream)`（成本预检/记账/错误提示全部沿用），**仅替换 system prompt 与上下文来源**。
- **降级安全网（关键）**：以下任一情况回退**直出 top1 原文**（faith 最安全）：
  1. LLM 未配置 / 成本熔断 blocked / 超时或网络异常；
  2. 合成输出包含拒答短语（「知识库中未找到相关信息」）——116b933 显示配额 4 下拒答应为 0，若仍出现说明片段真不够，直出 top1 比拒答更稳妥（top1 是全局最相似 chunk）。
  降级事件计入 metrics（见 §六）。
- **mode 值**：合成回答 `mode="synth"`（区分命中直出 `hit` 与兜底 `fallback`）。前端已验证 sources 渲染与 mode 无关（RagChat 只判 `sources.length`）→ **前端零改动**；U3 反馈面板按 mode 统计天然可区分。

### 3.4 sources 归属与缓存

- **sources 一律用广度视图**（含合成回答）：来源列表是用户点验入口，需要广度（116b933 裁定现网来源保持配额 1）。深度视图**只**做合成上下文，不出现在任何用户可见输出里。
- **缓存**：`retrieve()` 的 value 从单视图变 `(breadth, depth)` 双视图 → `cache.py::_CACHE_VERSION` **v3 → v4**，上线时清 `rag:search:*`（既有约定：key 不含策略维度，改结构必须升版本）。缓存体积约翻倍（5→10 条 chunk 文本），热点问题条目少，可接受。

## 六、回滚与监控

- **回滚**：`SYNTH_MODE=off` 重启即回现网（合成路径完全旁路）；Step 1 的双视图不影响任何用户可见输出，无需回滚。实验后清 `rag:search:*`（v4 结构升级期间）。
- **监控**：`/metrics` 新增 `synth_total` / `synth_degraded`（LLM 失败回直出）/ `synth_refused`（拒答回直出）；U3 反馈面板（`ae448dc`）按 `mode=synth` 观察 👍/👎 分布——**这是「multi_doc vs all」最终档位的长期证据来源**。

## 七、风险与开放问题

1. **深度视图对多文档问题的收益未单独验证**：116b933 的 faith/relev 提升主要由单文档问题贡献（+27.32/+30.66pp），配额 4 会把多文档问题的名额压给 top1 文档（多文档 cov 0.5031→0.4046）。→ Step 3 分桶报告是硬要求；若 `multi_doc` 桶 faith 不达标，备选方案是「多文档用广度视图合成、单文档用深度视图合成」（双视图按问题类型交叉，实现成本相同）。
2. **`all` 档的延迟体验**：命中路径从毫秒级变 1~3s（流式可缓解，U1 的生成中/断流提示已就绪）。直出的「快」本身是产品价值，这也是默认档位预期选 `multi_doc` 而非 `all` 的原因。
3. **缓存体积翻倍**：双视图 value 使热点缓存条目体积 ×2。若观察到 Redis 内存压力，可改存「depth 视图只存 chunk_id 列表、正文从候选池取」——列为后续优化，不进本期。
4. **合成答案的引用核验**：v1 提示词要求正文内联【来源:x】标注，前端 RagChat 现以 sources 列表渲染引用、不解析正文标注 → 正文里的【来源:x】会原样显示给用户。需在 Step 2 决策：保留（可读性略降但可点验）或复用 `parse_citations()` 剥离正文标记、并入 sources。**建议剥离**（v2 的动机已证明正文夹带标记伤可读性与 relevancy，但保留 v1 的分点结构——即「v1 行为 + 正文剥标」）。

### 8.2 A/B 结果（40 问，单/多各半，seed=42，总成本 ≈¥3.2）

| arm | faith | relev | coverage | 多文档 faith/cov | 单文档 faith/relev |
|---|---|---|---|---|---|
| direct（现网） | 1.0 | 0.8209 | 0.6025 | 1.0 / 0.305 | 1.0 / 0.7722 |
| **multi_doc** | **0.9867** | **0.8996** | **0.7025** | 0.9906 / 0.405 | 0.9828 / 0.9031 |

- **预登记判定 6 项全过**：两档 faith ≥0.965（分桶同判）、relev ≥0.8455、coverage ≥0.6025 → `multi_doc_pass=True` / `all_pass=True`。

### 8.3 两个实施中的关键发现（对评测方法论的修正）

1. **RAGAS 的 `retrieved_contexts` 必须与答案的生成依据一致**：首版冒烟把广度视图传给合成答案的裁判，faith 崩到 0.55（答案引用了 top1 文档的后续块，而广度上下文里没有这些块 → 被误判「无支撑」）。修正为按 arm 传各自 ctx（合成→深度、直出→广度）后 all 的 faith 回到 1.0。**教训：评测上下文 = 生成上下文，混用会系统性低估合成质量。**
2. **分流判据在本语料上退化为「恒合成」**：40 问中 38 问 sources ≥2 篇（域内同质文档 vsim 普遍 ≥0.65，P0-2 窄区间发现的又一次显形）→ multi_doc 与 all 几乎重合。保留判据的价值在于**语料异质化后**（如扩充更多不同主题文档）仍能对单文档问题保留直出逃生舱。

### 8.4 最终形态

- 默认 `SYNTH_MODE=multi_doc`（`SYNTH_MODE=off` 一键回退）；检索缓存 v4（双视图）。
- 用户可见变化：多文档/多数问题从「top1 原文直出」变为「合成答案（分点 + 来源合并，正文无标注残留）」；`mode="synth"` 可在反馈面板区分观察。
- 成本：每问命中 +1 次 DeepSeek 合成 ≈ ¥0.01，llm 限流 20/分与 CostTracker 熔断不变。
