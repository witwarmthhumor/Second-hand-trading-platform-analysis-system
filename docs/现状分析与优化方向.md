## 一、一句话结论

**问答侧（RAG）已经是一个质量闭环的成熟子系统；竞品侧是一个功能完整、但「数据近乎为空、监控是空壳」的骨架。当前最该做的不是继续堆功能，而是：①把竞品侧的监控链路真正跑通（补上它唯一缺的"活数据"）；②把两个大单体（App.vue 1765 行、rag.py 390 行）继续拆薄；③补上观测、权限、部署三块基础设施级短板。**

> ⚠️ v1.7.0 批注：上述结论中的三项建议**均已完成**（监控链路 `450faed` 前已通、单体已拆 M1~M3、观测/限流/认证/CORS 已补），且 RAG 已升级为「合成答案上线」的增强形态。以文首状态表为准。

**① 问答侧（RAG）—— 成熟、闭环**

> ⚠️ v1.7.0 批注：下表「空壳 / 监控是空壳 / 没有站点解析器」的描述**均已过时**——F1/F2 已落地（`crawler/parsers.py` + `_monitor_job` 实抓实比对），详见文首状态表。

| 维度 | 现状 |
|---|---|
| 功能 | 列表/待校对/录入/对比雷达/变化记录/设置/报告导出，API 齐全（1078 行后端） |
| 数据 | **competitors 仅 3 条**（闲鱼/转转/爱回收），`competitor_changes = 0` |

### 2.3 现状的主要矛盾

1. **竞品侧没有"活"**：监控空壳 → changes 永远是 0 → "变化记录"页永远空白 → 竞品分析这个产品核心价值（追踪竞品变化）目前是**纸面功能**。
2. **单体尚未拆完**：RagChat 已从 App.vue 抽出，但竞品侧 7 个 tab（list/pending/form/compare/changes/kb/settings）仍全部挤在 App.vue 里，共享一个超大状态集。
3. **基础设施缺位**：无结构化日志、无指标观测、无限流、无 CORS 显式配置、无自动化部署。

## 三、优化方向与优先级建议

> 优先级定义：**P0** = 建议 1–2 周内做（收益高、成本低或堵风险）；**P1** = 1–2 月内做；**P2** = 视业务节奏做。

### 3.1 功能扩展

| # | 方向 | 优先级 | 预期收益 |
|---|---|---|---|
| F1 | **补全站点解析器，让监控真跑起来** | **P0** | 竞品侧从"空壳"变"活系统"，变化记录/待校对产生真实数据，产品核心价值落地 |
| F2 | **监控抓取策略落地**（替换 `_monitor_job` 空壳） | **P0** | 同 F1，是 F1 的上游调度；每小时定时抓取→提炼→diff→落库变化 |
| F3 | 竞品「人工校对 → 入库」闭环打通 | P1 | 待校对页从"只有草稿"到"可流转"，形成情报生产流水线 |
| F4 | 问答侧多文档召回（query decomposition / 按文档保底各取 1 篇） | P1 | 单文档 coverage 1.00 的短板补上，复杂多文档问题答得更全 |
| F5 | 竞品数据接入问答上下文（对比类问题）的增强 | P2 | 已有 `competitors_context` 注入，可继续做结构化对比生成 |

**F1/F2 详解**：这是当前**收益/成本比最高**的一件事。`fetcher.py` 已具备通用抓取 + SSRF 防护 + 重定向校验，只差每个目标站点的解析器（闲鱼/转转的爱回收页面结构各异）。`main.py` 的 `_monitor_job` 目前是个占位符。补上「站点解析器 + 抓取策略 + diff 落库」，就能让 `competitor_changes` 从 0 变成真实数据，整个竞品侧立刻"活"起来。**注意**：这会触发 LLM 提炼费用，需先确认 LLM 额度，否则监控跑起来却全部熔断。

### 3.2 代码可维护性

| # | 方向 | 优先级 | 预期收益 |
|---|---|---|---|
| M1 | **拆薄 App.vue**（7 个竞品 tab 抽成组件，仿 RagChat 先例） | **P0** | 1765 行降到可维护区间；每个 tab 独立状态，改一处不牵动全局；便于后续并行开发 |
| M2 | **拆薄 rag.py**（390 行：会话 CRUD 与 ask 端点分层） | P1 | 端点职责单一，会话管理逻辑可复用、可独立测试 |
| M3 | 竞品侧共享状态收敛（当前 list/pending/compare 交叉引用） | P1 | 消除隐式耦合，减少"改 A 坏 B" |
| M4 | 统一错误处理与响应封装 | P2 | 前端处理异常更一致，减少 try/catch 散落 |

**M1 详解**：RagChat.vue（677 行）已经验证了「抽组件 + defineAsyncComponent 懒加载」这条路径可行（build 通过、独立 chunk）。竞品侧 7 个 tab 用同一模式拆成 `CompetitorList.vue` / `PendingReview.vue` / `CompetitorForm.vue` / `Compare.vue` / `Changes.vue` / `KbManage.vue` / `Settings.vue`，App.vue 只留登录、导航壳和路由级状态。预期 App.vue 从 1765 行降到 400 行以内。

### 3.3 性能优化

| # | 方向 | 优先级 | 预期收益 |
|---|---|---|---|
| P1 | **embedding 在线路径缓存增强**（当前每次 `query_embedding` 同步 httpx 直调 Ollama） | P1 | 检索命中路径延迟下降；缓存命中时零 embedding 调用 |
| P2 | 检索结果的 N+1 已修（`collection.get` 批量取回），继续排查 BM25 全量打分开销 | P2 | 7619 chunk 规模下 BM25 `get_scores` 全量计算，规模再涨需向量化/截断 |
| P3 | 会话历史 JSON 字段增长控制（messages 整表 JSON，无消息上限） | P2 | 防止长会话拖慢读写、撑大行体积 |
| P4 | 前端 echarts 按需引入 + 路由级懒加载 | P2 | 首屏包体积下降，加载更快 |

**P1 详解**：`embedding.py` 里 `query_embedding` 是同步 httpx（timeout 600），在线问答每次检索都要同步调一次 Ollama `/api/embed`。虽然检索结果有 Redis 缓存兜底，但缓存未命中时，这条同步 embedding 调用会成为路径上的固定开销。可考虑：embedding 客户端复用连接池、异步化、或对 query embedding 也做短期缓存。

> ⚠️ v1.7.0 批注：上述「同步 httpx 阻塞在线路径」的判断**已被证伪**——`rag_service.retrieve()` 全程在 `asyncio.to_thread(rtv.search, ...)` 中执行，同步 embedding 跑在工作线程、不阻塞事件循环；且问题级检索缓存命中时零 embedding 调用。此项已裁剪，勿再列回待办。

### 3.4 用户体验

| # | 方向 | 优先级 | 预期收益 |
|---|---|---|---|
| U1 | 问答「生成中」状态、失败重试、断流提示 | P1 | LLM 兜底失败/超时时用户不再"卡死无反馈" |
| U2 | 竞品空态引导（3 条数据时列表页给录入/抓取引导） | P1 | 新用户不迷茫，降低"这系统能干嘛"的困惑 |
| U3 | 反馈闭环可视化（👍/👎 结果回流到评测/调参） | P2 | 让反馈回路形成可见闭环，而非只落库 |
| U4 | 报告导出体验（进度、失败原因） | P2 | 长任务透明化 |

### 3.5 潜在风险（建议优先堵）

| # | 风险 | 优先级 | 说明 |
|---|---|---|---|
| R1 | **LLM 依赖与成本熔断**：rightapi.ai 网关余额有限，熔断阈值 1 元 | **P0** | 兜底问答、竞品提炼、报告生成全部依赖 LLM。一旦欠费，问答退化成"命中直出 / 未命中报错"，竞品监控提炼全部停摆。需明确 LLM 供应商 SLA 与降级策略 |
| R2 | **无结构化日志与指标观测** | **P0** | 目前只有 print 级日志，无请求日志、无错误聚合、无性能指标。线上出问题只能靠复现，排查成本高 |
| R3 | **无接口限流** | P1 | `/ask`、`/ask/stream` 等 LLM 接口无限流，恶意/异常调用可直接打穿 LLM 成本 |
| R4 | **认证薄弱**：默认 `admin/123456`，无密码强度校验、无登录失败锁定 | P1 | 弱凭证 + 无暴力破解防护，若部署到公网风险高 |
| R5 | **单机单进程部署**：检索器/缓存均为进程内单例，无水平扩展 | P2 | 当前规模无碍；多副本时缓存/检索器状态需外置 |
| R6 | CORS 未显式配置（依赖 FastAPI 默认） | P2 | 前后端分离跨域，生产环境需明确 |

## 四、落地路线图建议

按「堵风险 → 激活竞品 → 拆单体 → 提体验」的顺序：

1. **第 1 周（P0 风险）**：R2 结构化日志 + R4 认证加固（改默认密码、加登录失败锁定）+ R1 明确 LLM 降级策略。
2. **第 2–3 周（P0 激活竞品）**：F1 站点解析器 + F2 监控策略落地，让 `competitor_changes` 产生真实数据。
3. **第 4–6 周（P0/P1 拆单体）**：M1 拆 App.vue（竞品侧 7 组件）→ M2 拆 rag.py。
4. **第 2 月（P1 增强）**：R3 限流 + F3 校对闭环 + F4 多文档召回 + U1/U2 体验。
5. **第 3 月（P2 按需）**：P2/P3/P4 性能、U3/U4 体验、R5/R6 部署级。
