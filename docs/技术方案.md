# 技术方案

> 二手交易平台分析系统 — 技术实现文档
> 本文是产品设计文档（`docs/产品设计文档.md`）的技术配套，聚焦「怎么做」，不重复「做什么」。

## 一、技术选型总览

| 层 | 选型 |
|----|------|
| 后端框架 | FastAPI |
| ORM | SQLAlchemy 2.x（异步） |
| 数据校验 | Pydantic v2 |
| 数据库 | PostgreSQL（Docker 容器运行） |
| 数据库迁移 | Alembic |
| 爬虫 | httpx + BeautifulSoup4 |
| AI 接入 | 可插拔 LLM Provider 抽象层（先接当前对话模型） |
| 前端框架 | Vue 3 + Vite |
| UI 组件库 | Element Plus |
| 图表 | ECharts |
| HTTP 客户端 | Axios |

| 消息队列 | 不引入（库内状态机替代） |

| 版本管理 | Git（main + feat，Conventional Commits） |

## 二、选型理由

每一项选型回溯到产品文档的具体需求：

| 产品需求 | 选型决策 |
|----------|----------|
| 半自动采集 + AI 提炼 + 人工校对 | 异步爬虫（httpx）+ 可插拔 LLM + 库内状态机（draft / 待校对 / 已入库） |
| 多竞品对比 + 雷达图 | ECharts + 后端对比查询 API |
| 通用维度 + 扩展字段（不同平台类型） | PostgreSQL JSONB 存扩展字段，枚举可扩展 |
| 可维护性：新增平台类型无需重构 | JSONB 扩展字段 + 平台类型枚举表 |
| 展示「AI 工程落地能力」 | Provider 抽象层 + Pydantic 结构化输出（核心亮点） |
| 安全性：密钥不入库 | `.env` 进 `.gitignore`，提供 `.env.example` |
| 本地跑通、暂不部署 | Docker 提供 PostgreSQL，零配置 |

**关键取舍说明**：
- **不引入 Celery/消息队列**：单用户本地项目无并发压力，「待校对」用数据库状态字段表达即可；引入队列属过度设计。
- **爬虫用 BeautifulSoup4 而非 selectolax**：纯 Python 零编译，Windows 本地开发更省心，抓取量小性能非瓶颈。
- **前端选 Vue 3 而非 React**：后台 CRUD 类场景配 Element Plus 开发效率最高。

## 四、数据模型设计

### 竞品实体（核心表 `competitors`）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | 主键 | 自增 |
| name | String | 名称（必填） |
| type | String/枚举 | 平台类型：C2C 闲置交易/回收置换/质检转卖/资讯社区（可扩展） |
| positioning | String | 一句话定位 |
| website | String | 官网 |
| launch_status | String | 上线状态：已上线/内测/已下线 |
| features | Text | 核心功能 |
| target_users | String | 目标用户 |
| business_model | String | 业务模式 |
| pricing | String | 定价方式 |
| strengths | Text | 优势 |
| weaknesses | Text | 不足 |
| tags | JSONB/ARRAY | 标签 |
| remark | Text | 备注 |
| ext_fields | JSONB | **扩展字段**（不同平台类型的专属字段，可扩展无需迁移） |
| data_status | String | 数据流转状态：draft / 待校对 / 已入库 |
| created_at / updated_at | Timestamp | 时间戳 |

### 状态机（数据流转）

`data_status` 三种取值，流转如下：

```
        ┌─── 半自动采集 ───┐
        │                   ▼
     draft ──抓取/提炼──▶ 待校对 ──人工确认──▶ 已入库
        ▲                    │
        └────── 降级/驳回 ──┘
```

- **手动录入**：直接 `已入库`，不经过 `draft`。
- **半自动采集**：抓取 → AI 提炼 → `待校对` → 人工确认 → `已入库`。
- **`draft` 的进入方式**：半自动采集的抓取/提炼失败时，降级为草稿（`draft`），由人工补齐后走手动录入；已入库数据被驳回时也回到 `draft`。
- `draft` 与 `待校对` 的区别：`draft` 是「未完成/需补齐」的草稿，`待校对` 是「已提炼待人工确认」的中间态。

## 五、AI 提炼链路设计

### Provider 抽象层

```python
class LLMProvider(ABC):
    async def extract(self, content: str) -> CompetitorExtraction:
        """从网页内容提炼结构化竞品信息"""
```

- 默认实现：对接当前对话模型
- 预留：DeepSeek / OpenAI / 通义 等实现，通过配置切换

### 结构化输出

- 定义 `CompetitorExtraction` Pydantic schema，约束 LLM 输出字段。
- 用 JSON Schema 约束，确保 LLM 输出可校验、可入库。
- 提炼失败时降级为手动录入，不影响主流程。

### 校对流程

- 提炼结果状态置为 `待校对`，进入待校对列表。
- 人工确认/修正后置为 `已入库`。

## 九、接口限流设计（R3）

**要解决的问题**：`/api/rag/ask(stream)`、`/api/fetch`、`/api/changes/monitor`、`/api/report/export`、`/api/kb/rebuild` 都会触发 LLM 调用或重计算，此前完全无限流——一个脚本循环就能把 LLM 成本打穿。

### 分层设计

| 层 | 位置 | 职责 |
|----|------|------|
| 策略路由 | `app/rate_limit.py::select_policy` | 路径 + 方法 → 策略（昂贵 / 认证 / 普通），豁免探活与文档路径 |
| 主体识别 | `app/rate_limit.py::subject_for` | 已登录按 user id，匿名按客户端 IP；登录/注册固定按 IP |
| 计数算法 | `app/rate_limit.py::RateLimiter` | 滑动窗口日志（每 key 一个时间戳双端队列） |
| 拦截 | `app/middleware.py::RateLimitMiddleware` | 纯 ASGI 中间件，超限在**业务之前**短路返回 429 |

### 三档策略

| 策略 | 覆盖接口 | 默认阈值 | 维度 |
|------|----------|----------|------|
| `llm` | 问答 / 抓取 / 监控轮次 / 报告导出 / 重建索引 / Agent 运行触发 | 20 次/分钟（另有全局 60 次/分钟） | 用户 |
| `auth` | 登录 / 注册 | 10 次/分钟 | IP |
| `default` | 其余 `/api/*` | 120 次/分钟 | 用户 |

### 几个关键取舍

- **为什么用滑动窗口而非固定窗口**：固定窗口在边界处会出现 2 倍突发（第 59 秒打满 + 第 61 秒打满）；滑动窗口行为可预期，且本场景阈值只到「每分钟数十次」，每 key 最多存 limit 个浮点数，内存可忽略。
- **为什么中间件而非业务内判断**：被挡下的请求必须在**触达 LLM 之前**就返回，否则成本已经花掉。同时它注册在 `RequestContextMiddleware` **内层**，保证 429 也带 request_id、进访问日志与 4xx 状态分布。
- **为什么昂贵接口还要叠一层全局桶**：单用户额度挡不住「多账号轮流刷」，全局桶是成本兜底。
- **为什么认证接口按 IP 而非账号**：攻击者可换用户名喷洒，按账号计数挡不住；按 IP 与已有的登录失败锁定（按用户名）形成互补。
- **`X-Forwarded-For` 默认不信任**：直连暴露时信任该头等于把限流维度交给客户端伪造（改个 header 就绕过）。仅部署在可信反向代理之后才把 `RATE_LIMIT_TRUST_PROXY` 置 true。

### 观测与验证

- `GET /metrics` → `rate_limited_total` / `rate_limited_by_policy`（哪类接口在被刷）、`rate_limit`（当前阈值与在跟踪的 key 数）。
- 被限流请求会记 `WARNING` 级日志（含 policy / scope / path）。
- 429 响应带 `Retry-After`、`X-RateLimit-Limit`、`X-RateLimit-Remaining`，便于客户端退避而非盲目重试。
- 限流被关闭时，`/health` 的 `security_warnings` 会给出告警。

### 已知边界

限流状态是**进程内内存态**（与 `metrics` / `login_guard` 一致）。当前单进程部署，够用；多副本部署时实际阈值会被副本数放大，需换成 Redis 共享计数。
